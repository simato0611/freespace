# 強化学習による仮想通貨取引戦略 設計書
### 対象: GMO コイン レバレッジ取引 / 1 分足〜15 分足

---

## 0. 3 行まとめ

- **1 分足ごとに「目標ポジション比率」を決める逐次意思決定問題**として定式化し、PPO で解く。1/5/15 分足のマルチタイムフレーム特徴量を状態に入れ、コスト（スプレッド・スリッページ・建玉管理料 0.04%/日）を環境の中で実費として引く。
- **1 分足は「判断の頻度」であって「売買の頻度」ではない**。後述のコスト算術から、平均保有時間は **2〜8 時間**（1 日あたり往復 3〜10 回）に誘導する。これを外すと、どんな予測精度でもコストで負ける。
- **単一シードのバックテスト結果は信用しない**。5〜10 シードのアンサンブル × ウォークフォワード（purge & embargo 付き）× Deflated Sharpe で採否を決め、リスク管理は学習に任せず決定論的なレイヤ（`src/rlgmo/risk.py`）で外付けする。

## 1. 前提: GMO コイン レバレッジ取引の制度とコスト

| 項目 | 値 / 内容 | 設計への影響 |
|---|---|---|
| 対象銘柄 | `BTC_JPY`, `ETH_JPY`, `XRP_JPY` 等（末尾 `_JPY` がレバレッジ銘柄） | 現物銘柄（`BTC` 等）とはシンボルが別。API 呼び出しで取り違えない |
| レバレッジ | 個人は最大 2 倍 | エクスポージャ上限 = 有効証拠金 × 2。`EnvConfig.leverage_cap` |
| 取引手数料 | レバレッジ取引は無料 | 手数料 0 でも**スプレッドは実費**。ここを 0 と置くと机上の空論になる |
| 建玉管理料 | 建玉評価額の **0.04% / 日**（JST 06:00 時点の建玉に課金） | 日跨ぎに離散的なコスト。06:00 までの残り時間を状態に入れる |
| ロスカット | 証拠金維持率が一定水準（例 75%）を割ると強制決済 | 環境で再現し、到達時は大きな負の報酬 + エピソード終了 |
| 取引時間 | 原則 24 時間 365 日（定期メンテナンス時を除く） | メンテ時間帯はデータ欠損 + 建玉を動かせない。事前フラット化ルールを持つ |
| 板 | **取引所（板）で執行する**こと | 販売所のスプレッドは数十 bp 級で、この戦略は成立しない |
| API | Public: K 線・板・ティッカー / Private: 発注・建玉（HMAC 署名） | レート制限あり。`scripts/` の実装は間隔を空けて再試行する |

> **必ず確認**: 料率・課金時刻・ロスカット水準・メンテナンス時間は変更されうる。実装ではすべて `configs/*.yaml` のパラメータにしてある。運用前に公式の最新値で更新すること。税務上、国内の暗号資産損益は原則 雑所得・総合課税である点も設計（利確頻度）に影響する。

## 2. 最重要: コストの算術（この節が戦略の形を決める）

片道コスト = スプレッド/2 + スリッページ ≒ **2.5 bp**（BTC_JPY 平常時の想定。必ず `scripts/measure_spread.py` で実測すること）。往復 **5 bp**。

BTC の年率ボラを 60% とすると 1 日のボラは約 **314 bp**。保有時間 H 分のトレード 1 回のリターン標準偏差は `314bp × √(H/1440)`。「コストを払ってちょうど収支トントンになるために必要な**グロス**の年率シャープ」は次のとおり:

| 平均保有 H | 1 日の往復回数 | 1 トレードのσ | 往復コスト | **損益分岐グロス Sharpe** |
|---:|---:|---:|---:|---:|
| 5 分 | 288 | 18.5 bp | 5 bp | **87.6** |
| 15 分 | 96 | 32 bp | 5 bp | **29.2** |
| 60 分 | 24 | 64 bp | 5 bp | **7.3** |
| 240 分 (4h) | 6 | 128 bp | 5 bp | **1.8** |
| 720 分 (12h) | 2 | 222 bp | 5 bp | **0.6** |
| 1440 分 (1日) | 1 | 314 bp | 9 bp (建玉管理料込み) | **0.55** |

**結論**:

1. 1 分〜15 分でポジションを回す戦略は、Sharpe 30〜90 のグロス予測力を要求する。これは板情報・約定履歴・低レイテンシ執行を持つ本職の HFT の領域であり、**1 分足 OHLCV だけで到達できる水準ではない**。
2. したがって本設計では、**判断は毎分・保有は数時間**という形にする。1 分足の役割は「エントリー/エグジットのタイミングを 1 分粒度で最適化すること」と「急変時にすぐ縮小できること」であって、回転を上げることではない。
3. 回転率の抑制は 3 重に効かせる:
   - 環境が実コストを引く（`costs.py`）
   - 報酬に回転ペナルティを足す（`RewardConfig.turnover_penalty`）
   - 建玉の微小なズレでは発注しない（`EnvConfig.rebalance_tolerance`, `RiskLimits.min_trade_delta`）
4. 建玉管理料 4 bp/日 は「日跨ぎ 1 回 = 往復コストの 8 割」に相当する。06:00 JST 直前にポジションを畳むか持ち越すかは意味のある判断であり、そのための特徴量（`carry_sin`, `carry_cos`）を状態に入れている。

## 3. なぜ強化学習か（そして、どこには使わないか）

「次の 1 分の値動きを当てる」だけなら教師あり学習で足りる。RL を使う理由は、**当てた後にどうするかが逐次最適化問題**だからである。

| RL が本質的に効くところ | 理由 |
|---|---|
| ポジションの継続・積み増し・手仕舞い | 現在の建玉が次の行動のコストを変える（状態依存のコスト） |
| コストと期待リターンのトレードオフ | 「弱いシグナルでは動かない」を明示的に学習できる |
| 保有時間の内生的決定 | 割引報酬が「いつ閉じるか」を最適化する。教師ありのラベルは保有期間を固定してしまう |
| 建玉管理料のような期限付きコスト | 06:00 の課金を先読みした行動が価値関数に自然に入る |
| リスク調整（含み損の扱い） | 状態に口座情報を入れることで、局面に応じたサイズ調整を学習できる |

**RL に任せないもの**（学習された方策は分布外入力に対する保証がないため）:

- 最大ポジション・日次損失上限・ドローダウン停止・異常ボラ検知・データ鮮度チェック → すべて決定論的なリスクレイヤ（`src/rlgmo/risk.py`）で外付けする。
- 発注の可否（スプレッド異常時は執行しない、など）。

> ハイブリッドも有効: 教師あり（勾配ブースティング等）で「次の 30 分のリターン予測」を作り、その予測値を状態の 1 次元として RL に渡す。予測とポジション制御を分離でき、デバッグが容易になる。本リポジトリの特徴量パイプラインはそのまま流用できる。

## 4. データ設計

- **取得**: GMO Public API `/v1/klines`（`symbol=BTC_JPY&interval=1min&date=YYYYMMDD`）を日次で連続取得（`scripts/fetch_data.py`）。`openTime` はミリ秒 epoch。本実装では **バーのクローズ時刻を index** に正規化する（「その足の情報が使えるのはクローズ後」を型で守るため）。
- **期間**: 最低 2 年。レジーム（上昇・下落・レンジ・高ボラ・低ボラ）を最低 2 つ以上含むこと。1 年しかないデータで学習した方策は、次のレジームで壊れる。
- **上位足**: 1 分足から `label="right", closed="right"` で 5 分足・15 分足を生成し、`merge_asof(direction="backward")` で 1 分足グリッドに貼る（`data/resample.py`）。素朴な `reindex().ffill()` は**未確定の 15 分足終値を漏らす**ので使わない。
- **欠損**: メンテナンス・障害でバーが飛ぶ。欠損は補間せず、そのまま「時間が飛んだ」として扱う（前後を繋ぐと偽の値動きを作る）。学習エピソードは欠損をまたがないように区間を切るのが望ましい。
- **合成データ**: ネットワークのない環境で配線を検証するため `data/synthetic.py` を用意した。トレンドが人工的に強く、ベースラインが非現実的に良く出る。**性能評価には絶対に使わない**。

## 5. MDP の定式化

### 5.1 意思決定タイミングと執行規約

```
時刻 t のバーがクローズ
      └→ 特徴量 s_t を計算（t までの情報のみ）
             └→ 方策 π(a|s_t) が目標ポジション a_t を出す
                    └→ t+1 のオープンで成行約定（スプレッド + スリッページを支払う）
                           └→ t+1 のクローズまで新ポジションで評価
```

損益は「t クローズ → t+1 オープン（旧ポジション）」と「t+1 オープン → t+1 クローズ（新ポジション）」に分けて計算する。**同じバーの終値で判断して同じ終値で約定する実装はルックアヘッドであり、バックテストを数倍良く見せる**。

### 5.2 行動空間

離散 5 値: `a ∈ {-1.0, -0.5, 0.0, +0.5, +1.0}`（目標ポジション比率）。

実効エクスポージャ = `a × レバレッジ上限(2.0) × 有効証拠金 × ボラターゲット係数`。

- 離散にする理由: 学習が安定し、方策が確率分布として解釈できる（アンサンブル平均・確信度フィルタが自然に書ける）。連続行動（tanh + SAC/PPO）は微調整の回転が増えやすく、コスト面で不利。
- **ボラターゲット**: `係数 = clip(目標ボラ/実現ボラ, 0.05, 1.0)`。年率 60% の局面と 30% の局面で同じ建玉を持つのは、リスク管理として一貫しない。これによりリスクが一定に保たれ、学習側も「ボラ調整後の方向」に集中できる。
- 建玉は毎バー「有効証拠金 × 比率」に再調整される（定率運用）。含み損が出れば建玉が自動的に縮み、ロスカットは実質的に「1 バーでの大きなギャップ」でしか起きない。微小なズレでの無駄な発注は `rebalance_tolerance`（既定 2%）で抑える。

### 5.3 状態空間（約 67 次元）

| 軸 | 特徴量 | 各タイムフレーム |
|---|---|---|
| モメンタム | ボラ正規化リターン（ラグ 1,2,3,5,10,20） | 1m / 5m / 15m |
| 平均回帰・位置 | EMA(12,48) 乖離 / ATR、ドンチャン位置、RSI(14) | 1m / 5m / 15m |
| ボラティリティ | ATR/価格、EWMA ボラの平常比、Parkinson ボラ比（ジャンプ検出） | 1m / 5m / 15m |
| オーダーフロー代理 | 符号付き出来高不均衡（Lee-Ready 近似）、出来高の平常比 | 1m / 5m / 15m |
| トレンド品質 | Kaufman 効率比、ローソク実体比 | 1m / 5m / 15m |
| 執行 | 60 分 VWAP 乖離 / ATR | 1m |
| 時間 | 時刻・曜日の sin/cos、**06:00 JST 課金までの残り時間**、東京/欧州/米国セッション | — |
| 口座状態 | 現在ポジション、建玉使用率、含み損益（ボラ単位）、保有バー数、ドローダウン、当日損益 | — |

設計上の要点:

- **すべてスケール不変**にする。生の価格・出来高は入れない（BTC_JPY は数年で価格の桁が変わり、学習期間の水準に過学習する）。
- **標準化は因果的に**行う。学習データ全体の平均・分散で標準化するのは、テスト期間の統計量を学習に漏らす典型的なリークである。本実装は 7 日ローリングの中央値・IQR で標準化し、±5σ でクリップする（`causal_robust_scale`）。ロバスト統計を使うのは、暗号資産のジャンプで平均・分散が壊れるため。
- **口座状態を状態に入れる**ことが重要。入れないと MDP が非マルコフになり（同じ相場でも建玉によって最適行動が違う）、価値関数の学習が破綻する。

### 5.4 報酬

既定:

```
r_t = [ log(E_t / E_{t-1}) / σ_target ]  −  λ_turn·|Δa_t| / σ_target  −  λ_dd·ΔDD_t / σ_target
```

- `E_t` は**コスト控除後**の有効証拠金。取引コスト・建玉管理料は報酬ハックではなく実費として環境が引く。
- 対数を取るのは、複利成長率（＝対数効用、Kelly 的）を最大化するため。ボラ（`σ_target` = 目標年率ボラの 1 バー換算）で割るのはスケールを揃えて学習を安定させるため。
- `λ_turn`（既定 2 bp 相当）は「実コストだけでは足りない摩擦」を足すノブ。バックテストのスプレッド仮定が甘かった場合の保険でもある。
- `λ_dd` はドローダウン増分へのペナルティ。分散ではなく下方リスクだけを罰する。
- ロスカット到達時は追加の負の報酬（`bankrupt_penalty`）+ エピソード終了。
- **代替**: Moody & Saffell の Differential Sharpe Ratio（`reward.kind: dsr`）。シャープを直接最適化するオンライン形式で、リスク調整後リターンを目的にしたい場合に使う。

> **報酬設計で避けるべきこと**: 「勝率」「含み益」「予測の当たり外れ」を報酬にしない。いずれも損小利大の逆（損失を伸ばして利益を刈る挙動）を誘発する。報酬は**手数料込みの資金の増え方**であるべきで、それ以外は制約として表現する。

### 5.5 エピソードと割引

- エピソード長 1440 バー（1 日）。学習時は期間内のランダムな開始点から切り出す。
- 割引率 γ = 0.999（実効ホライズン ≒ 1000 分 ≒ 17 時間）。**日跨ぎコストを先読みできる長さ**を確保している。γ を 0.99（100 分）まで下げると、6:00 の課金や数時間保有の価値が見えなくなる。
- 終了: ロスカット / 日次損失上限 −2% / エピソード終端。

## 6. アルゴリズムと学習

### 6.1 PPO を既定にする理由

| 観点 | 判断 |
|---|---|
| サンプル効率 | 環境は自前の高速シミュレータ。オンポリシーの非効率は問題にならない |
| 安定性 | 報酬が小さくノイジー。クリッピング + アドバンテージ正規化が効く。DQN 系は Q 値のスケール推定が不安定になりがち |
| 出力の解釈 | 行動が確率分布 → 確信度フィルタ・アンサンブル平均が自然 |
| 実装量 | 依存を増やさず 300 行程度で書ける（`agents/ppo.py`） |

代替: 経験再利用を効かせたいなら QR-DQN / SAC-discrete、本番ログから学ぶ段階では CQL / IQL などのオフライン RL。

### 6.2 過学習対策（この分野では最重要）

1. **アンサンブル**: 5〜10 シードを学習し、行動確率を平均して期待ポジションを取る。単一シードの RL は**同じ設定でも Sharpe が ±1 以上ばらつく**。1 シードの良い結果は、ほぼ確実に運である。
2. **ドメインランダマイゼーション**: エピソードごとにコスト（スプレッド/スリッページ）を ±50% 揺らす。コスト仮定に依存しない方策だけが生き残る。
3. **小さいネットワーク + 正則化**: 2 層 MLP（256/128）+ LayerNorm + Dropout 0.1。LSTM/GRU は表現力より過学習が先に来る。まず MLP で基準を作る。
4. **エントロピー減衰**: 0.01 → 0.001。序盤は探索、終盤は確定的に。
5. **早期終了**: 検証区間の複合スコア（Sharpe − 3×|最大 DD|）が最良の重みを採用する。学習曲線の最終点ではなく最良点を使う。
6. **特徴量を増やしすぎない**: 60 次元前後。似た情報の指標を 200 個入れると、検証成績は上がってテスト成績は下がる。

### 6.3 ハイパーパラメータ（既定値と勘所）

| パラメータ | 既定 | 勘所 |
|---|---|---|
| `lr` | 3e-4（線形減衰） | 大きすぎると方策が一方向に張り付く |
| `n_steps` × `n_envs` | 512 × 8 = 4096 | 1 更新あたり最低 4k サンプル |
| `epochs` | 4 | ノイジーな環境で回しすぎると過学習 |
| `gamma` | 0.999 | 日跨ぎコストを見るための長さ |
| `gae_lambda` | 0.95 | 分散とバイアスの標準的な妥協点 |
| `clip_range` | 0.2 | 標準 |
| `target_kl` | 0.03 | 超えたら早期打ち切り |
| `ent_coef` | 0.01（自動調整） | 目標エントロピーへの乗算制御。上限 0.1 |
| `explore_eps` | 0.10 → 0.01 | 一様分布の混合率。**エントロピー崩壊の予防に最も効く** |
| `cost_curriculum_start` | 0.25 | 序盤のコスト倍率。検証・テストは常に実コスト |
| `bc_steps` | 50,000 | モメンタム則の行動クローニングによる暖機 |
| `shared_trunk` | false | 方策と価値で胴体を分ける。共有すると価値損失が方策表現を壊す |
| `reward_scale` | (1−γ) | 価値ターゲットを O(1) に。アドバンテージ正規化により方策勾配は不変 |

### 6.4 「常にフラット」という罠（この環境で最初にぶつかる壁）

取引環境には **報酬 0 の強力な局所解**がある。何もしなければコストを払わず、報酬はちょうど 0 になる。
一方、探索的に売買すればスプレッドを即座に払うので報酬は必ず負から始まる。
その結果、標準的な PPO は数万ステップで「常にフラット」に収束し、方策エントロピーが 0 に潰れて探索が止まる。

実際にこの実装で観測された挙動（合成データ、5 万ステップ時点）:

```
step= 52,224 reward/bar=-0.0042 H=0.012   ← エントロピーが潰れ、方策は「フラット」に固着
```

本設計では 3 つの対策を組み合わせている。

1. **探索の下限（一様分布の混合）**（`explore_eps_start`）: 行動分布を `(1-ε)·π + ε·U` とし、
   ε を 0.10 → 0.01 へ減衰させる。これが最も効いた。純粋な softmax 方策は、いったんエントロピーが
   0 に潰れると**エントロピーボーナスの勾配自体も消えて復帰できない**（実測: 係数を上限まで上げても
   H=0.017 のまま張り付いた）。一様分布を混ぜておけば行動確率に下限 ε/|A| が入り、勾配が消えない。
2. **目標エントロピー制御**（`adaptive_entropy`）: エントロピー係数を固定値にせず、実測エントロピーが
   目標（序盤 0.6×ln|A| → 終盤 0.05×ln|A|）を下回れば係数を上げ、上回れば下げる乗算制御。
   崩壊「後」の復帰には効かないため、上の ε 混合と併用する。
3. **コストカリキュラム**（`cost_curriculum_start`）: 学習序盤はコストを 1/4 に軽くし、
   学習の 30% を使って実コストへ戻す。先に「方向性のシグナル」を学ばせ、後から「コストへの慎重さ」を学ばせる。
   最終的な方策は必ず**実コストで**検証する（検証・テスト環境のコストは常に 100%）。
4. **行動クローニングによる暖機**（`bc_steps`）: モメンタム則のような粗い教師を数万ステップ模倣してから
   PPO を開始する。探索が「取引する側」から始まるため、フラットの谷に落ちない。
   教師の性能自体は重要ではない（PPO が上書きする）。初期値の置き場所を変えるだけの措置である。

> それでも数十万ステップでフラットのままなら、報酬スケール（`σ_target`）と `turnover_penalty` の
> バランスを疑う。回転ペナルティが実コストより大きいと、設計上フラットが最適解になってしまう。

### 6.5 実装の健全性確認（合成データ）

実データが無い環境でも、**学習機構そのものが機能しているか**は合成データで確認できる
（`configs/smoke.yaml`）。本実装で観測された典型的な学習経過:

| 学習ステップ | 検証 Sharpe | 回転/日 | 状態 |
|---:|---:|---:|---|
| 修正前 50k | 84 | 3.7 | いったん学習するが… |
| 修正前 150k〜 | **0** | 0 | エントロピー崩壊 → 常にフラットへ退行 |
| 修正後 50k | 82 | 7.4 | 教師（モメンタム則）と同等 |
| 修正後 350k | 82 | **3.7** | 収益を保ったまま回転率が半減（＝コスト効率の学習） |

**合成データの成績は戦略の収益性の根拠にはならない**（生成モデルにトレンドを埋め込んで
あるため、モメンタム則ですら Sharpe 84 が出る）。ここで見るべきは
「①学習が発散しないか ②フラットに退行しないか ③回転率が下がる方向に進むか」の 3 点だけである。

## 7. 検証プロトコル

### 7.1 ウォークフォワード（purge & embargo 付き）

```
[  学習 90 日  ][embargo 1日][ 検証 15 日 ][embargo 1日][ テスト 15 日 ]   → 15 日ずつ前進
```

- **embargo**: 特徴量のローリング窓が境界をまたいで情報を運ぶのを防ぐギャップ。
- **検証区間だけで**ハイパーパラメータ・特徴量・報酬・早期終了を決める。
- **テスト区間は最終評価に一度だけ**使う。テスト成績を見て設計を直した瞬間、その成績はインサンプルになる。
- 通常の k-fold・シャッフル分割は時系列では厳禁。

### 7.2 ベンチマーク（必ず並べる）

`flat`（常にノーポジ）/ `long`（Buy & Hold）/ `momentum`（15 分足モメンタムの符号）/ 教師あり線形モデル。**これらに勝てない RL は採用しない**。特に `flat` に負ける場合、そもそも回転しすぎている。

### 7.3 指標

年率 Sharpe / Sortino / 最大ドローダウン / Calmar / 日次勝率 / 平均保有時間 / 1 日あたり往復回数 / コスト控除前後の PnL / コストドラッグ（年率）/ ロング・ショート別の寄与。

### 7.4 統計的な有意性

- **Deflated Sharpe Ratio**（`metrics.deflated_sharpe`）: 「何通り試したか」を正直に数えて割り引く。試行数にはシード・ハイパラ・特徴量セットの試行をすべて含める。
- 目安として、1 年ぶんのデータで推定した Sharpe の標準誤差は **±1 程度**ある。「バックテスト Sharpe 2.5」は「真の Sharpe は 0.5〜4.5 のどこか」を意味する。fold 間で符号が揃うかどうかの方が、平均値そのものより重要。

### 7.5 ストレステスト（採用前に必ず）

| 試験 | 内容 | 合格ライン |
|---|---|---|
| コスト倍加 | スプレッド・スリッページを 2 倍 | Sharpe が正のまま |
| 執行遅延 | 約定を 1 バー遅らせる | 大幅劣化しない |
| 不利約定 | 常に不利側 1 bp で約定 | 同上 |
| ボラショック | 急落局面（例: 数分で −15%）を注入 | ロスカットに触れない |
| データ欠損 | 30 分の欠損を挿入 | フラット化して復帰する |
| シード分散 | 10 シードの Sharpe 分布 | 下位 25% でも正 |

## 8. 採用ゲート（この数字を満たさなければ本番に出さない）

1. ウォークフォワードの **fold の 70% 以上で Sharpe > 0**、平均 Sharpe > 1.0（コスト後）。
2. `flat` / `long` / `momentum` すべてに Sharpe で勝つ。
3. コスト 2 倍のストレス下でも Sharpe > 0。
4. Deflated Sharpe の p 値 > 0.95（試行数を正直に数えて）。
5. 最大ドローダウン < 15%、1 日の最悪損失 < 5%。
6. 平均保有時間 > 60 分、1 日あたり往復回数 < 20（コスト算術との整合）。
7. ペーパートレード 4 週間で、実測コスト・約定価格がバックテスト仮定の範囲内。

## 9. 本番運用

### 9.1 実行ループ（`scripts/live_paper.py`）

```
毎分バークローズ +2 秒
  → 最新 1 分足を取得（学習時と同一の特徴量コードで再計算）
  → アンサンブルで目標ポジション（期待値 Σ p_i·a_i、|期待値| < 閾値ならフラット）
  → リスクレイヤでクリップ（rlgmo/risk.py）
  → 現在建玉との差分だけを発注（min_trade_delta 未満は見送り）
```

**学習時と推論時で特徴量コードを共有すること**（別実装にすると必ずズレる。これは実運用で最も多い事故）。

### 9.2 リスクレイヤ（学習に任せない部分）

| 制約 | 既定 | 動作 |
|---|---|---|
| 最大ポジション | 1.0 | クリップ |
| 日次損失上限 | −2% | 当日フラット・新規停止 |
| 累積ドローダウン | −5% で縮小 / −10% で完全停止 | 停止からの再開は人手 |
| ボラ上限 | 年率 150% | サイズを比例縮小 |
| スプレッド異常 | 片道 8 bp 超 | 執行しない（現状維持） |
| データ鮮度 | 90 秒 | 発注しない |
| 連敗ブレーキ | 6 連敗 | 60 バーのクールダウン |
| 証拠金維持率 | 150% 未満 | 建玉を半減 |

### 9.3 監視

- **分布ドリフト**: 本番の特徴量分布と学習期間の分布（KS 検定・PSI）。乖離したら縮小。
- **行動分布**: 方策のエントロピー、ポジション比率のヒストグラム。学習時と大きく違えば異常。
- **実測 vs 想定**: 約定価格と想定コストの差を毎日集計。想定を超え続けるならコストモデルを更新して再学習。
- **成績の CUSUM**: 累積損益の傾きが検証期間の下限を割ったら自動停止。
- API エラー率・レイテンシ・注文拒否率。

### 9.4 再学習と資金投入

- 週次でウォークフォワードを 1 コマ進めて再学習 → 検証 → シャドー運用 1 週間 → 差し替え。
- 資金は段階的に: 最小サイズ 2 週 → 1/4 → 1/2 → フル。各段階で採用ゲートを再確認する。

## 10. 失敗モードのチェックリスト

- [ ] 同一バーの終値で判断・約定していないか（ルックアヘッド）
- [ ] 標準化に将来データを使っていないか（`StandardScaler().fit(全期間)` は禁止）
- [ ] 上位足を `ffill` で貼っていないか（未確定足の漏れ）
- [ ] スプレッドを実測したか（「手数料無料」を「コスト 0」と読んでいないか）
- [ ] 建玉管理料を入れたか（日跨ぎで 4 bp/日）
- [ ] テスト区間を見て設計を直していないか
- [ ] 単一シードの結果で判断していないか
- [ ] 学習と推論で特徴量コードが同一か
- [ ] 出来高・価格の生値を特徴量に入れていないか（水準への過学習）
- [ ] 平均保有時間がコスト算術と整合しているか
- [ ] ロスカット・維持率をシミュレータに入れたか
- [ ] メンテナンス時間帯・データ欠損時の挙動を決めたか

## 11. 拡張案（基本形が動いてから）

1. **階層化**: 上位（15 分足）が「レジーム/方向」、下位（1 分足）が「執行とサイズ」を担当する 2 層方策。本設計は単一エージェントにマルチタイムフレーム特徴量を与えることで実質的に両方を扱っているが、明示的に分けると解釈性が上がる。
2. **板情報の追加**: WebSocket の板・約定履歴から、板の傾き・約定の偏り・キャンセル率を状態に加える。短期の予測力はここに最も多く残っている。
3. **教師ありハイブリッド**: 「30 分後リターンの予測値」を特徴量として注入し、RL はサイズと保有だけを決める。
4. **複数銘柄**: BTC_JPY と ETH_JPY を同時に扱い、相関を使ったヘッジ・分散。行動空間は銘柄ごとの目標ポジションのベクトルになる。
5. **オフライン RL**: 本番の意思決定ログが溜まったら CQL / IQL で「実際に起きたこと」から学習し、シミュレータと現実のギャップを埋める。
6. **執行の最適化**: 成行ではなく指値・分割執行を行動空間に入れる（別 MDP として切り出すのが実務的）。
