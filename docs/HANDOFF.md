## 1. 戦略の中身（これが全て）

コードを読まなくても再現できるよう、判断ロジックを言葉で書く。

### 1.1 シグナル — トレンド・ラダー

各銘柄について、1 時間足で 4 本のトレンドを測る。

```
lookback ∈ {5日, 14日, 30日, 60日}
trend(L) = (log終値 − L本前のlog終値) / (日次ボラ × √L)
signal   = mean(trend(5), trend(14), trend(30), trend(60)) / 1.5    → [−1, +1] にクリップ
```

- **単一のルックバックを選ばない**のが要点。4 本平均にすることでパラメータ選択への
  当てはめが薄まり、2 つの独立した時代の両方で成績が上がった（時代A 0.94→1.01、時代B 1.59→1.86）
- **両建て（long_only = false）**。単一銘柄ではショート側は負けるが、複数銘柄に分散すると
  下落局面の収益源になる（2018年 −0.13→+1.74、2022年 +0.52→+1.09）
- **リバランスバンド 0.10**: シグナルが 0.10 以上動いたときだけ建て直す。微小な揺れに
  スプレッドを払い続けるのを防ぐ

### 1.2 サイジング — 2 段階のボラ目標

```
1段目（銘柄ごと・等リスク）:
    scale_i = clip(0.15 / 実現ボラ_i, 0, 2.0)
    建玉_i  = clip(signal_i × scale_i, −0.5, +0.5)      # 有効証拠金比

2段目（ポートフォリオ全体）:
    pf_scale = clip(0.15 / ポートフォリオ実現ボラ, 0.2, 5.0)   ※1本ラグ
    建玉_i  ×= pf_scale

3段目（レバレッジ上限）:
    Σ|建玉_i| > 2.0 なら全体を比例縮小
```

実現ボラの窓は銘柄 20 日 / ポートフォリオ 60 日。**平均グロス建玉は 0.24 倍**で、
レバレッジ上限 2.0 には普段まったく触れない（ロスカットは極めて遠い）。

### 1.3 執行 — 2 つの速度

| ループ | 間隔 | 見るもの | できること |
|---|---|---|---|
| リスク監視 | **60 秒** | データ鮮度・スプレッド・証拠金維持率・DD・日次損失 | 縮小 / 全決済 / 発注見送り |
| リバランス | **1 時間** | トレンド・ラダーの再計算 | 目標との差だけ発注 |

- 判断を 5 分に速めても改善しない（実測で 5分〜8時間に有意差なし、細かいほど DD は悪化）。
  一方リスク事象は分単位で起きるので、**監視だけ**を速くした
- **最小発注幅 0.005**: これ未満の建玉変更は発注しない。発注が 1 日 120 回 → 11 回に減るが
  成績は連続リバランスと同じ（§7 の較正記録を参照）
- **リスク判定の解釈に注意**: 「データが古い」「板が壊れている」は**発注見送り（建玉は維持）**であって
  全決済ではない。日次損失上限・累積 DD 停止のときだけ畳む。ここを間違えると
  いちばん約定が悪い場面で成行を投げることになる

## 3. Desktop でやること（この順序で）

### ステップ 1 — 環境確認と、基準データの検証

```bash
git checkout claude/rl-crypto-trading-strategy-hb5qqb

# 基準データの完全性と、基準の数字が再現できるかを確認する

```

検証の基準になる価格データは `data/handoff/` に同梱してある（`git clone` だけで手に入る）。
中身の説明は [`data/handoff/MANIFEST.md`](../data/handoff/MANIFEST.md)。既存スクリプトが
期待するパスに置くなら:

```bash
mkdir -p data/raw
cp -r data/handoff/prices/perp_1h        data/raw/perp
cp -r data/handoff/prices/alt2017_1h     data/raw/alt2017_1h
cp -r data/handoff/prices/verify_sources data/raw/verify_sources
```

**判定**: テストが 73 件通り、`verify_bundle.py` が
「全期間 1.577 / 開発期間 1.696 / ホールドアウト 1.059」を再現すること。
**再現しないまま GMO のデータを取っても、食い違いの原因を切り分けられない。**

### ステップ 2 — GMO 実データの取得 ★最重要

```bash
for S in BTC_JPY ETH_JPY XRP_JPY LTC_JPY BCH_JPY; do
  python scripts/fetch_data.py --symbol $S --interval 1min \
    --start 2021-04-16 --end 2026-08-25 --out data/raw/gmo/${S}_1min.parquet
done
```

- GMO の K 線提供は **2021-04-16 以降**。約 4.4 年ぶん取れる
- 1 日 1 リクエストなので 5 銘柄 × 約 1,600 日 = 8,000 回。`--sleep 0.5` で **約 70 分**
- 欠損バーの報告が出る。**大きな空白（数時間以上）がある期間はメモしておく**

**判定**: 5 銘柄すべてで 2021-04-16 以降が概ね埋まっていること。

### ステップ 3 — データの健全性検証 ★これを飛ばさない

過去に**公開データの破損で検証結果が丸ごと無意味になった事故がある**（§7）。
価格水準もボラも正常なのに、バーの時刻が実際の値動きと対応していなかった。
欠損・重複チェックでは検出できない。

```bash
# GMO の BTC_JPY と、既にある Binance perp BTC を突き合わせる
python scripts/verify_data.py \
  --a data/raw/gmo/BTC_JPY_1min.parquet \
  --b data/raw/perp/BTC_1h.parquet --freq 1h --by-year
```

**判定基準**:
- 時間足リターン相関 **≥ 0.95 → 正常**、0.80〜0.95 → 要確認、**< 0.80 → 破損の疑い**
- JPY 建てと USD 建ての差（為替）で相関は 0.99 までは行かない。**0.95 を超えれば合格**
- `--by-year` で年ごとに見る。**特定の年だけ落ちるパターンが最も危険**
- ETH / XRP も同様に。LTC / BCH は突き合わせ相手がないので、
  **BTC_JPY との相関が他の暗号資産並み（0.6〜0.8）にあることだけ確認**する

**ここで破損が見つかったら、その銘柄・期間を除外して §4 のルールのもとで再検証すること。**

### ステップ 4 — GMO 実データでの再検証

**`scripts/gmo_validate.py` が引き継ぎ用に用意した検証スクリプト。**
バックテスト用のパラメータを別に持たず、**本番設定 `configs/gmo_live.yaml` を直接読む**ので、
「検証したものと動かすものが違う」事故が起きない。1分足でも自動で1時間足に畳む。

```bash
# GMO 実データで本番設定をそのまま検証（判定まで自動で出る）
python scripts/gmo_validate.py --dir data/raw/gmo --config configs/gmo_live.yaml --btc BTC_JPY

# 比較の基準（海外データでの現在の到達点）。先にこちらを走らせて挙動を確認するとよい
python scripts/gmo_validate.py --dir data/raw/perp --symbols BTC ETH XRP BNB DOGE
```

**比較の基準となる海外データでの結果**（このコマンドで再現できる）:

| 区間 | Sharpe | 年率 | 最大DD | BTCベータ | 月次勝率 | 発注/日 |
|---|---:|---:|---:|---:|---:|---:|
| 全期間（6.2年） | 1.58 | 30.0% | −14.1% | −0.01 | 61.3% | 10.9 |
| 開発期間 | 1.70 | 32.8% | −14.1% | 0.00 | 61.7% | 10.7 |
| **ホールドアウト（15か月）** | **1.06** | 19.0% | −8.5% | −0.15 | 60.0% | 12.1 |

**GMO 実データでこれと大きく食い違ったら、まず §3 ステップ3 のデータ検証に戻ること。**
戦略ではなくデータを疑うのが先である（§6 の罠を参照）。

**判定（GO/NO-GO ゲート）** — `gmo_validate.py` が自動で出力する:

## 4. 守ってほしいルール（禁止事項）

このプロジェクトは**「検証の作法」を守ったことだけが価値**である。ここを崩すと
5.7 年ぶんの検証が全部無意味になる。

1. **ホールドアウト（2025-01-01 以降）でパラメータを調整しない。**
   既に 1 回使った。数字が悪くても、それは「悪いという情報」であって
   「調整すべきという合図」ではない。再調整した瞬間、その期間はもう検証区間ではなくなる

2. **成績が悪かったからといってパラメータを触らない。**
   ルックバック・gain・ボラ目標・バンド幅は全て開発期間だけで決めた。
   後から動かすのは後知恵の当てはめである。**変えたくなったら、変えた理由と
   変える前の数字を `docs/strategy_search.md` に必ず記録してから変えること**

3. **新しい試行は必ず記録する。** 現在 139 試行。Deflated Sharpe はこの数で補正している。
   黙って試すと補正が効かなくなり、統計的な主張が嘘になる

4. **「たぶん大丈夫」で先へ進まない。** 各ステップに判定基準を書いた。
   基準を満たさないまま次へ行くと、どこで壊れたか永久に分からなくなる

5. **RL を再挑戦するなら、まず `docs/strategy_search.md` の 3 節と 30 節を読む。**
   2 回（うち 1 回は正常データで）試して 2 回とも単純ルールに負けている。
   同じことを 3 回目にやる前に、何が違うのかを言語化すること

6. **バックテストとライブでサイジングを二重実装しない。**
   両者は `portfolio.compute_exposures()` を共有しており、テストで固定している。
   ライブ側だけ書き換えるとサイレントにズレる

## 6. 過去に踏んだ罠（同じ穴に落ちないため）

| 罠 | 症状 | 対処 |
|---|---|---|
| **公開データの破損** | 価格水準もボラも正常なのに、バーの時刻が値動きと対応していない。欠損チェックを素通りする | `verify_data.py` を作った。**新しいデータを入れたら必ず走らせる** |
| コストが安すぎる仮定 | 1〜15分足で「勝てる」ように見える | 損益分岐 Sharpe を先に計算する（5分足なら 106 が必要。到底無理） |
| RL のエントロピー崩壊 | 常にフラットを出力して学習が止まる | 一様混合の探索フロア + 適応エントロピー + コストカリキュラム + BC ウォームスタート |
| 価値関数の暴走 | vf loss 133 で方策が学習できない | 方策と価値のトランクを分離、報酬に (1−γ) を掛ける |
| `action_repeat` でコストが消える | サブバーのコストが集計されない | trade_cost / carry_cost / pnl / turnover を累積 |
| 日次損失上限がエピソードを打ち切る | バックテスト期間が 810→511 日に縮む | `_blocked` フラグでその日だけフラット、翌 JST 日に再開 |
| ライブのリスク判定の誤解釈 | 「板が壊れている」で全決済 → 最悪の場面で成行 | `:hold` 系の理由は発注見送りに分類。テストで固定 |
| 最小発注幅が粗すぎる | 建玉 0.03〜0.07 に対し閾値 0.05。ほとんどの調整が無視される | 0.005 に較正。発注 120→11 回/日、成績は不変 |

## 8. 判断のまとめ

**この戦略は「自己資金で小さく始め、実績を作る」段階にある。**
検証の作法・リスク管理・実装の整合は個人運用の水準を超えているが、
実績がゼロで、GMO の実データを一度も見ていない。

機関投資家の水準ではない。理由は戦略の質ではなく、
①ライブ実績ゼロ ②キャパシティ未測定・単一カウンターパーティ ③検証期間の短さ、の 3 点である。

**Desktop 側の最大の貢献は、§3 のステップ 2〜4 で「GMO の実データでも同じ結論が出るか」を
確かめること。**ここで結論がひっくり返る可能性は本当に残っている。
ひっくり返ったらそれが正しい答えなので、素直にそう記録してほしい。
