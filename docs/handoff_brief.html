時間でしか解決しないもの

ホールドアウト15か月の独立した方向転換は 44回しかない。Deflated Sharpe は 0.11（試行139本の補正後）で採用ゲート不合格。「真の Sharpe が 1.0 か 0.3 か」は今のデータでは判別できない。 戦略の欠陥ではなく、データ量の問題である。実運用の期待は 0.5〜0.8 と見ておくのが正しい。

03

引き継ぎ手順

順序に意味がある。各ステップに判定基準を置いた。基準を満たさないまま次へ行くと、 どこで壊れたか永久に分からなくなる。

1

環境確認

通らなければ環境の問題。先へ進まない。

git checkout claude/rl-crypto-trading-strategy-hb5qqb
pip install -e .
python -m pytest tests -q      # 73件 全通過するはず
2

GMO 実データの取得 最重要

K線の提供は 2021-04-16 以降、約4.4年ぶん。1日1リクエストなので5銘柄で約70分かかる。

for S in BTC_JPY ETH_JPY XRP_JPY LTC_JPY BCH_JPY; do
  python scripts/fetch_data.py --symbol $S --interval 1min \
    --start 2021-04-16 --end 2026-08-25 --out data/raw/gmo/${S}_1min.parquet
done
判定 — 5銘柄すべてで 2021-04-16 以降が概ね埋まっていること。大きな空白はメモしておく。
3

データの健全性検証 飛ばさない

過去に公開データの破損で検証結果が丸ごと無意味になった事故がある。価格水準もボラも正常なのに、 バーの時刻が実際の値動きと対応していなかった。欠損・重複チェックでは検出できない。

python scripts/verify_data.py \
  --a data/raw/gmo/BTC_JPY_1min.parquet \
  --b data/raw/perp/BTC_1h.parquet --freq 1h --by-year
判定 — 時間足リターン相関 ≥ 0.95 で正常。JPY建てとUSD建ての差があるので 0.99 までは行かない。 --by-year で年ごとに見ること。特定の年だけ落ちるパターンが最も危険。
4

本番設定での再検証

この引き継ぎのために用意したスクリプト。バックテスト用のパラメータを別に持たず、 本番設定ファイルを直接読むので「検証したものと動かすものが違う」事故が起きない。GO/NO-GO まで自動で出す。

python scripts/gmo_validate.py --dir data/raw/gmo \
  --config configs/gmo_live.yaml --btc BTC_JPY
判定 — 下のゲート表を参照。数字が低く出てもパラメータを触ってはいけない。 まずデータを疑う（ステップ3に戻る）。
5

実効スプレッドの実測と発注仕様の反映

発注仕様は推測で書かない。/v1/symbols のレスポンスに minOrderSize / maxOrderSize / sizeStep が銘柄ごとに入っている。 それを使って scripts/live_gmo.py:148,152 の .4f 固定を置き換える。テストを先に書くこと。

python scripts/measure_spread.py --symbol BTC_JPY --minutes 60 --size 0.01
curl -s https://api.coin.z.com/public/v1/symbols | python -m json.tool
判定 — 実測スプレッドが片道8bp以内なら想定の範囲（損益分岐は22bp）。

ドライラン（最低1か月）

既定がドライラン。GMO_API_KEY / GMO_API_SECRET は環境変数から読む（コードに書かない）。

04

守ってほしいルール

このプロジェクトは検証の作法を守ったことだけが価値である。ここを崩すと 5.7年ぶんの検証が全部無意味になる。

01
ホールドアウト（2025-01-01以降）でパラメータを調整しない 既に1回使った。数字が悪くても、それは「悪いという情報」であって「調整すべきという合図」ではない。 再調整した瞬間、その期間はもう検証区間ではなくなる。
02
成績が悪かったからといってパラメータを触らない ルックバック・gain・ボラ目標・バンド幅は全て開発期間だけで決めた。後から動かすのは後知恵の当てはめ。 変えたくなったら、変えた理由と変える前の数字を docs/strategy_search.md に必ず記録してから変える。
03
新しい試行は必ず記録する 現在139試行。Deflated Sharpe はこの数で補正している。黙って試すと補正が効かなくなり、統計的な主張が嘘になる。
04
「たぶん大丈夫」で先へ進まない 各ステップに判定基準を書いた。基準を満たさないまま次へ行くと、どこで壊れたか永久に分からなくなる。
05
RLを再挑戦するなら、まず記録を読む 2回（うち1回は正常データで）試して2回とも単純ルールに負けている。3回目をやる前に、何が違うのかを言語化すること。
06
バックテストとライブでサイジングを二重実装しない 両者は portfolio.compute_exposures() を共有し、テストで固定している。 ライブ側だけ書き換えるとサイレントにズレる。
05

過去に踏んだ罠

同じ穴に落ちないために。全34節の詳細は docs/strategy_search.md にある。

罠症状対処
公開データの破損価格もボラも正常なのに、バーの時刻が値動きと対応していないverify_data.py を作った。新データは必ず通す
コスト仮定が甘い1〜15分足で「勝てる」ように見える損益分岐 Sharpe を先に計算する（5分足なら106が必要）
RLのエントロピー崩壊常にフラットを出力して学習が止まる探索フロア + 適応エントロピー + コストカリキュラム + BC
日次損失上限の副作用バックテスト期間が 810→511日に縮むその日だけフラット、翌JST日に再開
リスク判定の誤解釈「板が壊れている」で全決済 → 最悪の場面で成行発注見送りと全決済を分類。テストで固定
最小発注幅が粗すぎる建玉0.03〜0.07 に対し閾値0.05。調整がほぼ無視される0.005 に較正。発注120→11回/日、成績は不変
